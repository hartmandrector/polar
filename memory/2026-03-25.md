## Key Gotchas Found
- `findTrim(airspeed, config)` — airspeed first, config second (not the other way)
- `numericalJacobian(trim.state, config)` — state first, config second
- `NaturalMode` interface uses `realPart/imagPart/frequency_Hz/dampingRatio/timeToHalf_s` (not sigma/omega_n/omega_d/zeta)
- Script output path: use `import.meta.url` for ESM compatibility, not `__dirname`

## Late Evening — Canopy Estimation + 3D Rendering in GPS Viewer

### Canopy Estimator (canopy-estimator.ts) — commit 99d7037
- **New file**: `src/gps-viewer/canopy-estimator.ts`
- Ported acceleration-decomposition algorithm from CloudBASE Kotlin (`canopyblxr.kt`)
- Pipeline: measured accel → subtract gravity → project onto velocity (drag) → reject (lift) → subtract pilot body drag (CdA model) → residual = CN force → normalize × lineLength = canopy position
- AOA from CN-velocity angle geometry + trimOffset (default 6°)
- **Orientation is airspeed-based** (canopy is a weather vane): ψ = atan2(vE, vN), θ = γ + α·cos(φ), φ = aero roll
- CN geometry orientation was tried first but looked wrong — canopy faces into relative wind, not where lines point
- Config: lineLength=3m, pilotCd=0.35, pilotS=0.5m² (slick), pilotMass=77.5kg, trimOffset=6°, minAirspeed=5m/s

### Key Decisions
- **Canopy position = pilot position** — cp2.gltf origin is riser convergence, no offset needed
- **Airspeed-based orientation, not CN-geometry** — canopy is a weather vane, faces into relative wind
- **80° hang angle for pilot** (not 90° — slight forward lean looks more natural)
- **Flight computer mode gates canopy visibility** — no canopy during wingsuit/freefall
- **Two separate GPSAeroOverlay instances** — one for wingsuit segments, one for canopy cells. Swap at mode boundary.
