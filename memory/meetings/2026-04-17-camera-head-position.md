## Summary

Implemented a second head orientation source for the GPS viewer using Insta360 X5 camera quaternions exported from Gyroflow. The camera data drives the head GLB model with priority over the existing FlySight fused sensor. Config is persisted in `sync-result.json` alongside the track data in `public/`, enabling fully automatic loading from the URL on subsequent visits.

Session spanned research (Gyroflow quaternion conventions, existing head sensor code), architecture design with Q&A, and multi-file implementation across the GPS viewer stack.

---

## Decisions Made

- **Camera priority over fused sensor**: When both sources available, camera quaternion drives the head model
- **File picker for manual load**: Standard browser file dialog for gyroflow CSV (not path prompts — those are painful to use)
- **Config stored in `sync-result.json`**: In `public/<trackFolder>/` alongside the GPS track — not localStorage. This follows the same pattern as other per-track data and enables URL-based auto-load
- **Gyroflow CSV stays in cloud storage**: Large files (186k+ rows at 1kHz) remain in OneDrive logbook. The absolute path is stored in `sync-result.json` and fetched via Vite `/@fs/` at dev time
- **Mount offset approach**: Post-multiply `camera_quat × inverse(mount_rotation)` with heading/pitch/roll sliders. Default pitch = -20° for selfie stick forward tilt
- **Gyroflow quaternion convention**: Unknown precisely — using best-guess NWU remap (same as fused sensor) with mount offset sliders for empirical correction
- **Sync offset from `sync-result.json`**: `pipeline_time_ms = camera_timestamp_ms + offsetMs` (same offset generated by `video-sync.ts`)
