# 2026-04-13 — GPS Viewer Rotation Visualization + Fixed Orientations Pipeline

## Arc Visualization Redesign
- **Outer arcs (r=1.2, bold):** Changed from aerodynamic torque (N·m) → **angular velocity ω (p, q, r)**
- **Inner arcs (r=0.9, pale):** Changed from angular velocity → **angular acceleration ω̇ (ṗ, q̇, ṙ)** — straight derivative of body rates
- Rationale: torque arrows can be misleadingly large when inertia is big (canopy); angular acceleration is what the control solver actually matches against and is more intuitive
- `ACCEL_SCALE = 0.5` (tunable), torque contributions move to controls decomposition section
- Committed color renames: `COL_RATE_*` → `COL_ACCEL_*`

## Fixed Orientations Pipeline (`fix-orientations.ts`)
- New `FixedOrientation` type on `GPSPipelinePoint.fixed` — parallel to `aero`/`bodyRates`, never overwrites originals
- Fields: `roll, theta, psi, p, q, r, pDot, qDot, rDot`
- Three-phase computation:
  1. Phase-corrected Euler angles per flight phase (ground/exit/deploy/canopy/freefall)
  2. Unwrap + LS derivative + inverse DKE → fixed body rates
  3. LS derivative on fixed rates → fixed angular accelerations
- Phase corrections:
  - **Ground:** roll=0, pitch=π/2, heading from flyingIndex (stable)
  - **Exit (pushoff→flying):** smoothstep slerp, heading locked to flyingIndex
  - **Deployment:** smoothstep from frozen wingsuit pose to canopy hang angles
  - **Canopy:** canopy estimator angles when valid
  - **Freefall/wingsuit:** pass-through from aero extraction
- Wired into `gps-main.ts` on initial load + `recalcCanopy()` slider changes
- Overlay arcs prefer `pt.fixed.*` with fallback to `pt.bodyRates.*`

## Exit Transition Fixes (gps-scene.ts + body-frame-scene.ts)
- Standing heading now locked to `flyingIndex` heading (was per-frame `pt.aero.psi` — garbage on ground)
- Ground heading also locked to flyingIndex (eliminates wild spinning)
- Linear lerp → smoothstep for exit transition
- Both scenes updated consistently

## Key Architecture Decision
- Hartman decided on **additive fixed fields** (Option 1) over overwriting originals (Option 2) — keeps raw pipeline data intact, gives flexibility for downstream consumers, avoids breaking existing code paths
- This sets up the pattern for future pipeline corrections: always add a corrected channel, never destroy the original
