Pre-optimization baselines (speed chart active, sim running):

- Keyboard held: 6.4fps, 155ms avg
- Gamepad: 6.7fps, 149ms avg

## Root Cause

The dominant cost was NOT the sweep math (0.17ms for 5040 Kirchhoff evaluations).
It was `chart.update('none')` → Canvas 2D drawing 720 individually-colored line segments
× 2 charts ≈ 33ms per call. This fired every sim frame.

Original code called `rebuildChart1()` + `rebuildChart2()` (destroy + `new Chart()`)
on every `updateChartSweep()` call. That added ~17ms of JS overhead on top of the
canvas draw, for a total of ~50ms per frame just for charts.

Key insight: even after switching to in-place updates (P1), canvas draw still costs ~33ms
because 720 calls to `strokeStyle` + `stroke()` are expensive regardless of in-place vs
rebuild. The chart draw cost scales with the number of individually-colored segments.

---

## Fixes Implemented

### P1 — In-place chart data updates (`polar-charts.ts`)
Added `updateChart1DataInPlace()` and `updateChart2DataInPlace()`. Datasets, colors,
segment callbacks, and plugin state are updated on the live chart instance without
destroy/recreate. `rebuildChart1/2` still called for view switches and legacy toggle.
Saved: ~17ms/frame. 9.4fps → 11.2fps.

### P2a — 5Hz chart update throttle (`main.ts`)
`SWEEP_THROTTLE_MS = 200`. All chart updates (sweep + cursor) are skipped on throttled
frames. Physics, readout, vectors, Three.js render at full rate. On throttle tick: check
sweep key; call full sweep or cursor-only as appropriate.
Saved: ~55ms/frame. 11.2fps → 29.8fps.

Combined result: **9.4fps → 29.8fps** (3.2×). p95: 203ms → 97ms.

### `responsive: false` — ATTEMPTED, REVERTED
Setting `responsive: false` on charts eliminates the `_computeLabelSizes` forced reflow
(~7ms) but breaks DPR handling — Chart.js normally sets `canvas.width = cssWidth × dpr`
for crisp rendering. With `responsive: false`, canvas is at CSS pixels only → blurry on
any display with DPR > 1. Reverted. `responsive: true` preserved throughout.

## What Was NOT Done (future work — see `docs/PERFORMANCE.md`)

**Phase P3 (cheap wins):**
- Singleton empty Map in `getSegmentPolarOverrides()` (Issue 4)
- Module-level THREE temporaries in `main.ts` (Issue 6)
- Remove `performance.now()` / `console.log` from `computePilotCouplingDerivatives` (Issue 7)

**Phase P4:** Deduplicate `sumAllSegments` calls (currently called twice per frame).

**Phase P5:** Cache `computeInertia`, `computeCenterOfMass`, `buildPilotCoupling` in
`getSimConfig` callback (called every physics frame, runs full recompute unnecessarily).

**Phase P6 — Input-driven polar cache invalidation (key insight from user):**
Current 5Hz time throttle is a blunt instrument. The polar curve shape depends on PILOT
INPUTS (pitch/roll/yaw throttle, hipCamber, legBend, brakes, beta, delta, dirty) — NOT
on airspeed. Better strategy:
- Tier 1 (≤50ms): redraw immediately when any control axis changes by > 0.005, or
  delta/dirty change, or vehicle switch
- Settling pass: one additional redraw at +150ms after a Tier 1 trigger to capture beta
  settling after roll/yaw inputs
- Tier 2 (2s): background catch-all for slow rho (density altitude) drift — rho can be
  bucketed to nearest 0.05 kg/m³
- Remove airspeed from sweep key entirely (Kirchhoff at current fidelity is effectively
  velocity-independent across wingsuit operating range)

**Canvas draw cost alternatives:**
- **`createLinearGradient` for the polar line** — replace 720 individual `strokeStyle`
  changes with one CSS gradient across the x-axis and a single `stroke()` call. Estimated
  10–15× faster (~2ms vs 33ms). The color represents AOA linearly along α-axis which is
  already the chart x-axis, so visual output is nearly identical. Best near-term fix.
- **OffscreenCanvas + Web Worker** — moves the 33ms canvas draw off the main thread
  (physics never blocked), but Chart.js doesn't support workers without significant DOM
  shimming. Only practical if Chart.js is replaced with raw Canvas 2D or WebGL.
- **WebGL chart library** — handles 720 points in microseconds on GPU; large refactor.

## Flight Server Architecture (explored, not implemented)

The user raised the idea of running the polar project as a pure physics server and
connecting an external renderer (Unreal Engine or CesiumJS) via WebSocket/UDP.

Key findings:
- The physics core (`sim.ts`, `eom.ts`, `aero-segment.ts`) is already pure TypeScript
  with no DOM dependencies — can run in Node.js today with no changes
- `FlightState` is a clean serializable data contract; at 60Hz JSON over WebSocket = ~30KB/s
- Browser can't be a WebSocket server; best path is to extract sim to Node.js and have
  both the polar visualizer and CesiumJS connect as clients
- CesiumJS globe rendering + real terrain would enable trajectory validation against real
  GPS tracks (connects naturally to the existing GPS viewer and CloudBase integration work)
- Three.js stays as the close-up debug/tuning view (better for force vectors, model
  segment inspection); CesiumJS handles macro trajectory and terrain context

Not pursued this session — captured as a future architecture direction.
