# 2026-03-05 Session Notes

## Canopy Riser Tuning — Final Resolution

### Gamepad Mapping Root Cause
- The gamepad stick-to-riser variable NAMES were backwards from Hartman's mental model the entire time
- Push forward = front risers (Hartman's convention). Code was mapping forward to `rearRiser` variable
- Fixed by swapping the mapping AND swapping all tuned constant values to preserve behavior
- **Lesson**: when debugging control feel, verify variable names match the user's physical model first

### Final Riser Architecture
**Front risers** (push forward):
- `ALPHA_MAX_FRONT_RISER: 6` (α decrease)
- `RISER_PITCH_MAX_RAD: -0.35` (~20° **nose-up** tilt — NEGATIVE is the only stable config)
- `FRONT_RISER_CM: -0.15` (nose-down pitching moment — this is what creates the dive/speed increase)
- `FRONT_RISER_CD_BUMP: 0` (disabled)

**Rear risers** (pull back):
- `ALPHA_MAX_RISER: 6` (α increase)
- `REAR_RISER_PITCH_MAX_RAD: 0.06` (~3.4° nose-up tilt)
- `REAR_RISER_CM: +0.10` (nose-up pitching moment)
- `REAR_RISER_CD_BUMP: 0` (disabled)

### Key Finding: CM is Essential for Realistic Front Riser Response
- Without CM, front riser α decrease gets canceled by system seeking new lift equilibrium (AoA actually goes UP)
- The pitching moment forces the system trim point down — this is what makes you go steeper/faster
- Drag bump on fronts also fought the α decrease (created nose-up moment via aft CP shift)

### Brake Tuning
- `BRAKE_PITCH_MAX_RAD: 0.14` (~8°) — increased from 0.06 for more turn authority
- `BRAKE_CD_BUMP: 0.12` — increased from 0.08 for more turn authority
- Turn comes from asymmetric tilt + drag, not just α offset

## Phase Architecture Discussion (Late Evening)

### Key Decisions
- **Remove LB/RB gamepad vehicle cycling** — dangerous with running sim (crashes on unbuilt vehicles), opaque. Vehicle/phase selection moves to UI panel exclusively.
- **FSM control via UI, not gamepad** — more robust, explicit, shows state clearly
- **Nested status panel design** — outer scenario box → inner phase box → sub-state box during deployment. Each level shows relevant telemetry.
- **Per-phase telemetry**: freefall gets Δh/Δd from exit; deployment gets g-force/snatch/deploy%; canopy gets AGL/glide/brake%; landed gets summary stats

### Connection to GPS Flight Computer
- Hartman noted the phase FSM maps directly to the GPS dynamic model switching problem
- Both need to detect current flight phase from available data (sim uses physics, GPS uses sensor fusion)
- Phase detection heuristics are shared knowledge between sim and flight computer domains

### Robot Machine Context
- Hartman built a similar FSM for the VR wingsuit simulation robot rig project
- That project used a finite state machine orchestrating the full simulation — same architectural pattern we're applying here
