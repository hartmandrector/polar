# 2026-03-11 — Late Night Session: Pilot Pendulum Euler Singularity Fix

## Problem
Pilot stays inverted during canopy flight after steep-climb deployment. Root cause: canopy Euler angle θ passes through ±90° singularity during pitch-down from deployment (~140°) to trim (~6°). After singularity passage, θ drifts to garbage values (265°, -170°, etc.). Canopy flies OK because aero forces self-correct via body-frame velocity feedback, but the pilot pendulum computes gravity from state.theta → gets wrong gravity direction → pilot settles at wrong equilibrium.

## Key Insight
At θ=-170°, `gx_body = -g*sin(-170°) = +0.174g` — gravity x-component FLIPS sign vs correct θ=6° value. Pendulum gravity pulls pilot forward instead of backward. This is a fundamental Euler 3-2-1 representation problem, not a formula bug.

## Solution: Body-Frame Gravity Vector Tracking
Instead of computing gravity from corrupted Euler angles, track a body-frame gravity unit vector (gx, gz) as auxiliary state:
- Initialized from deployment θ: `gx = -sin(θ)`, `gz = cos(θ)`
- Integrated each step via rotation kinematics: `ġx = -q·gz`, `ġz = q·gx`
- Renormalized to unit length each step (prevents numerical drift)
- Pendulum uses gx/gz directly — bypasses Euler singularity entirely

### Files Modified
- `sim-state.ts` — added `gravBodyX`, `gravBodyZ` to SimStateExtended; added derivatives to SimDerivatives
- `sim.ts` — pendulum passes gx/gz instead of state.theta; computes gravity vector derivatives; integrates + renormalizes in forwardEuler; RK4 averaging
- `eom.ts` — `pilotPendulumEOM` signature changed: takes `gx_body, gz_body` instead of `thetaCanopy`; diagnostic logs show gx/gz
- `deploy-canopy.ts` — initializes gravBodyX/Z from deployment θ; removed UNSTABLE_LIMIT clamp (no longer needed); restored thetaPilot = bodyState.theta
- `sim-runner.ts` — initializes gravBodyX/Z for freefall start state

1. **Cap θ at 90°** — Hartman rejected: canopy IS below pilot in steep climb, gravity IS upward in canopy frame. Correct physics, not an error.
2. **Euler angle wrapping to [-π,π]** — θ still settled at -170° (wrong side of singularity). Wrapping doesn't fix the underlying representation problem.
3. **thetaPilot = -theta** (force equilibrium) — Hartman rejected: θp must be wingsuit pitch at deploy time.

### Root Cause: Gravity Vector in Translational EOM Destabilizes Canopy
- During turns, body rates (p,q,r) all active → gravity vector integration drifts
- Since gravity vector was used in canopy translational EOM, drifted gravity → wrong forces → canopy diverges (V=NaN, α=NaN)
- **Fix**: Reverted translational EOM to use original `gravityBody(phi, theta)` — gravity vector now ONLY used by pendulum
- Canopy no longer diverges, but pendulum still has violent dynamics

### Real Root Cause: riserLength = 0.5m Makes Pendulum Way Too Fast
- Period = 2π√(0.5/9.8) = 1.4 seconds — any canopy pitch change causes massive angular acceleration
- Real parachute system: pilot hangs from 4-5m of lines+risers from canopy rotation center
- Period with 4m: 4 seconds, 1/8th the angular acceleration → gentle swings like reality
- Currently: 5° canopy pitch change → pendulum accelerates at ~2 rad/s² → 25° overshoot in 0.5s

### Feedback Loop (now disabled but was major problem)
- Pilot pitch → rotatePilotMass() → changes segment positions → changes canopy moments → changes canopy pitch → changes pilot gravity → loop
- Disabled BOTH directions: coupling torque = 0, pilotPitch not fed back into aero model
- Even with feedback disabled, pendulum still too aggressive due to riserLength

## Session 4 (~10:30-11:00 AM): THE ACTUAL FIX — Gravity Torque Sign Error

### Root Cause Found
Compared current code to original commit `b5a21a1` (the working pre-deployment pendulum). Original gravity torque:
```
τ = -m·g·l·sin(θp - θc)
```
Our gravity vector translation had:
```
τ = m·g·l·(cos(θp)·gx - sin(θp)·gz) = -m·g·l·sin(θp + θc)
```
**Plus instead of minus on θc.** The `sin(θp)·gz` term had the wrong sign.

### Correct Formula
```
sin(θp - θc) = sin(θp)·cos(θc) - cos(θp)·sin(θc) = sin(θp)·gz + cos(θp)·gx
τ = -m·g·l·(sin(θp)·gz + cos(θp)·gx)
```

### Also Fixed
- Coupling sign: was `+Iy*qDot`, original had `-Iy*qDot`
- Reverted sim-ui.ts fully to original values (riserLength=0.5, pitchSpring=5, pitchDamp=70% critical)
- Translational EOM uses `gravityBody(phi,theta)` not gravity vector (reverted earlier this session)
- Pilot→canopy aero feedback still disabled (cosmetic pendulum)

### Result
- Canopy flies stable again ✅
- Deployment doesn't get stuck upside down ✅
- Pendulum behaves normally during turns ✅
- Deployment-specific swing/IC tuning deferred to later

### Lesson
All the tuning (spring/damp/coupling/riserLength changes) was compensating for a fundamental sign error. Once the sign was correct, original parameters worked perfectly.

## Session 5 (~12:00-1:30 PM): Weight Shift Reclassification + Doc Updates

### Critical Architecture Decision: Weight Shift ≠ Physical Rotation
Hartman clarified the correct model for pilot-canopy control inputs:

- **Weight shift** = pure **aerodynamic control** (Kirchhoff blending), same category as brakes/risers. Pilot shifts hips → changes riser loading → warps canopy shape. No mass/CG change, no pilot rotation, no pendulum physics. The existing `pilotLateralEOM()` with stiff spring is WRONG — should be removed/repurposed.
- **Line twist** = physical **yaw rotation** with real restoring torque from line geometry. Needs 3D rendering (pilot yaw) + static slider. Does NOT change canopy Kirchhoff parameters.
- **Pilot pitch** = physical swing (existing pendulum, cosmetic only, feedback disabled)

### Key Insight
Weight shift changes the **canopy** (aero, shape) but not the **pilot** (mass, orientation).
Line twist changes the **pilot** (orientation, visual) but not the **canopy** (aero).
