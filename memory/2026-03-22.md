### Pipeline data flow:
1. Parse GPS file (auto-detect format)
2. SG smooth velocity (multi-pass, configurable windows)
3. LS acceleration from smoothed velocity
4. Geodetic → NED position (direct conversion, NOT integration)
5. SG smooth position (same windows as velocity — important for replay)
6. Wind correction + WSE aero extraction (kl/kd/roll → CL/CD → α via polar table match)
7. Flight computer mode detection (step 5 in pipeline)
8. Mode-specific processing (wingsuit segments vs canopy — future)

### Key design decisions:
- **Wind convention: meteorological "from"** — `airspeed = groundVelocity + windVector`. North wind (from north) adds to northward airspeed. Addition not subtraction.
- **Position from measurements, not integration** — geodetic→NED via flat-earth + avg latitude correction (haversine fallback for long distances). Hartman explicitly rejected velocity integration.
- **Smoothed position via SG filter** — same windows as velocity. Raw position preserved as lat/lon/hMSL. Smooth position (posN/E/D) for replay and frame transforms.
- **No legacy WSEQPolar** — removed CloudBASE polar types entirely. AOA estimation uses pre-built system polar table from our own segment model (swept externally via sweepSegments, passed as SystemPolarPoint[]).
- **wse.ts is pure** — no imports from `../polar/` or `../viewer/`. Polar table built externally, passed in via config. Clean separation.
- **Flight computer ported from BASElineXR** `restorewindfilter` branch — `EnhancedFlightMode.java` → `flight-computer.ts`. 8 modes (Unknown/Ground/Plane/Wingsuit/Freefall/Deploy/Canopy/Landing). Gated transitions (must go through Deploy to reach Canopy). Sustained speed deploy detection (vxs < 19 after established). Dual-rate (fast per-sample + slow 1Hz). `processAll()` for batch post-processing.

## Wingsuit Flight Range Discussion

- **Current top-end: ~2:1 glide** at α ≈ -1.3°. Hartman wants **1:1 glide** (realistic for aggressive forward push).
- Real physics: suit partially deflates, arm sweep changes, leg position opens → kills lift and adds drag simultaneously.
- Approach: progressive "dirty" modifier at low/negative α — increase cd_0, reduce effective cl_alpha as suit loses pressurization. SymmetricControl already supports d_cd_0 and d_cl_alpha per unit δ.
- Stall behavior is already pretty good — hard to pull all the way back, sensitive to camber at stall point.

## Acro / Back Flying Discussion

- Hartman asked about belly↔back transitions, barrel rolls, acro maneuvers
- **Two-polar approach recommended**: belly polar + back polar with lerp transition (like unzip does wingsuit→slick)
- Back polar: reversed camber baseline (negative alpha_0), different CP, lower L/D. Stable around -44 m/s at ~3:1 glide with camber manipulation.
- Transition: Y button triggers timed barrel roll (1-2s), polar lerps during rotation
- Knife-edge phases (β=90°): simplified tumble drag model where neither polar is valid
- Challenge: current controller profile is belly-flying only. Acro needs full attitude envelope.

## Input Filter Discussion

- **EMA filter recommended** between gamepad and aero model: `filtered += (raw - filtered) * (1 - e^(-dt/τ))`
- **Separates feel from physics**: filter handles how responsive stick feels, aero coefficients tuned purely for realism. Without filter, only way to reduce twitch is changing aerodynamics (bad tradeoff).
- **Key insight**: gamepad stick goes 0→100% in ~50ms, real wingsuit shoulder shift takes 0.5-1s. Filter bridges this mismatch.
- **Per-axis time constants (initial):**
  - Wingsuit: pitch τ=0.12s, roll τ=0.05s, yaw τ=0.08s
  - Canopy: brakes τ=0.03s, risers τ=0.08s, roll τ=0.03s, yaw τ=0.05s
- Handles variable dt naturally. One line per axis. Configurable per vehicle mode.
- **Hartman agreed this should go in before further coefficient tuning** — tune aero for realism first, then filter for feel.

## Eigenvalue Analysis — Inner Wing + Center CM/CP Tuning Session

### Baseline saved (`a5segments-baseline.json`) at start of session

### Experiment 1: Inner wing cp_0=0.15→0.25, cm_alpha=-0.20→-0.10, cm_0=0.01→0.03
- Short period went UP slightly (+0.04–0.11 Hz across envelope) — wrong direction
- Reason: moving CP back reduced destabilizing lift-arm faster than reducing cm_alpha reduced stabilizing direct moment → net Mα slightly increased
- Dutch roll at 30 m/s: went from unstable (ζ=-0.027) to stable (ζ=0.135) — nice lateral improvement
- Trim α and γ unchanged — lift/drag preserved

### Experiment 2: + Center cm_alpha=-0.255→-0.15 (keeping inner wing changes)
- Short period dropped ~5% (1.951→1.905 Hz at 50 m/s) — right direction but small
- Dutch roll at 30 m/s: excellent (ζ=0.535)
- Still 2.7× too stiff vs GPS (1.9 Hz vs 0.7 Hz target)
- qDot crossover shifted slightly (positive at 40 m/s now)

### Key insight: CP-lift interaction dominates pitch stiffness
- Explicit cm_alpha terms are NOT the main source of Mα
- CP positions forward of CG create lift-dependent restoring moment that dominates
- Even at cm_alpha=0 on all segments, forward CPs would still create strong pitch stiffness
- Center CP at 0.36 (0.04 fwd of CG 0.40) with S=1.03 m² is the biggest contributor
- To reach 0.7 Hz target: need ~86% reduction in total Mα → (0.7/1.9)² ≈ 14% of current
- Next suggestion: move center cp_0 from 0.36 → 0.39 (nearly at CG) to kill lift-arm stiffness
