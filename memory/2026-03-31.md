## Sensor Fusion EKF Design — Research & Architecture

### Context
- Madgwick algorithm too blind — binary rejection, no uncertainty model, no external reference injection, heading especially weak
- Hartman discovered dynamic calibration offsets work as a heading knob — motivates proper external reference integration
- Flying filter (GPS + aero model) produces heading/pitch/roll that should feed into sensor fusion

### Decision: Error-State Quaternion EKF (Solà formulation)
- Industry standard (VectorNav, Xsens, PX4)
- Separates nominal state (400 Hz gyro integration) from error state (EKF on perturbation)
- Error always small → linearization always accurate
- 9-state: δθ(3), δb_gyro(3), δb_mag(3)
- External references (flying filter orientation) as first-class measurements with adaptive R
- Continuous R scaling replaces binary rejection (accel magnitude → R_accel scaling, mag field deviation → R_mag scaling)

## Multi-Device Complementary Fusion — Hartman's Ideas (afternoon session)

### Multiple IMU Placement Concept
- **Head**: FlySight 2 (current) — orientation, head tracking
- **CG / belly pocket**: Second device in belly of wingsuit or lower back below container — closer to actual CG, less head movement noise
- **Canopy bridle attachment point**: Pocket built into canopy at bridle — direct canopy orientation sensing
- Algorithm should be **flexible enough to handle different device placements** as measurement sources — not hardcoded to head-only
- Design implication: measurement models should be parameterized by mounting position (known lever arm offset from CG)

### Integration Order Insight (Hartman)
- In dynamics EKF: **position-first** integration is typical to control coupling between derivative states
- Contrast with simulation (our sim-runner): RK4 starts with **rotation first** → mass distribution → acceleration → velocity → position
- The order matters for numerical coupling — worth documenting in filter architecture
- Hartman reviewing PDFs on phone (Solà, Markley, Kalman) before diving deeper

### Flight Controller as Filter Orchestrator — Key Architectural Insight
- Sensor data means completely different things in different contexts (standing on ground vs sitting backwards in airplane vs flying)
- Filters produce GARBAGE if expected mode doesn't match actual situation
- Flight controller (BASElineXR / companion app) must orchestrate:
  - Which filters are active per flight phase
  - GPS dynModel switching via UBX-CFG-NAV5 over BLE (already documented in GPS-FLIGHT-COMPUTER.md, 2026-02-28)
  - Sensor data rates (40ms to 200ms via BLE)
  - Walking vs vehicle vs airborne mode for u-blox internal EKF
  - Sensor fusion EKF measurement model selection (which measurements are valid per phase)
- GPS-FLIGHT-COMPUTER.md already has flight phase table: Ground→Airplane→Exit→Freefall→Wingsuit→Deployment→Canopy→Landing→Post-landing
- Each phase needs: different dynModel, different rate, different filter configuration
- The sensor fusion EKF's adaptive R and measurement gating must be driven by the flight controller's phase FSM
- Integration order matters: dynamics EKF typically does position-first to control derivative coupling; simulation does rotation-first (RK4) because causality flows moments→angular accel→orientation→forces→linear accel→velocity→position
- Filter chaining: flight controller orchestrates which filters feed which, mode-dependent
