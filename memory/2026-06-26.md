- **`updateEnvironment(env, camera, elapsedMs)`**: integrates flow velocity into `_flowOffset`, wraps it, passes `uCameraPos`/`uFlowOffset`/`uTime` to shaders.
- **Flow velocity** gives speed sensation: particles stream from nose to tail in body mode, relative to airspeed and current α/β.

### Canopy Mass Constants Extracted (`polar-data.ts`)
- `CANOPY_STRUCT_RATIO_PER_CELL = 0.00643` — fabric/structure per cell (×7 cells ≈ 3.5 kg at 77.5 kg system mass). Used in `CANOPY_STRUCTURE_SEGMENTS`.
- `CANOPY_AIR_RATIO_PER_CELL = 0.011` (exported) — trapped air per cell (×7 ≈ 6 kg). Used in `CANOPY_AIR_SEGMENTS`.
- Air is excluded from weight (buoyant) but included in inertia (resists rotation). `computeCenterOfMass()` uses weight segments; `computeInertia()` uses inertia segments.

### Deployment Slider CG-Tracking Bug Fix (`main.ts`)
**Root cause**: `sliderModel` is a sibling of `compositeRoot` in `loadedModel.group` (world space). `pilotPivot.position` is LOCAL to `compositeRoot`. `applyCgFromMassSegments` shifts `compositeRoot.position` when CG changes (e.g. when tuning `CANOPY_STRUCT_RATIO_PER_CELL`), so the pilot visually moves but the slider bottom (which used raw local coords) stayed fixed → slider intersected pilot's head.

**Fix**: both slider branches (`d > 0 && d < 1` and `d >= 1`) now add `mp = currentModel.model.position` to `pilotPivot.position` before using it as world-space bottom position.

**Hierarchy reminder**:
```
loadedModel.group  (at world origin)
├── compositeRoot (= loadedModel.model) ← shifted by applyCgFromMassSegments
│   └── pilotPivot  ← LOCAL position
├── bridleGroup    ← also shifted by applyCgFromMassSegments
└── sliderModel    ← positioned in group/world space  ← fix was here
```

## Commit 2: Console Trim-Capture Commands (`__polar.writeVelocityVector`)

### What Was Built
Four DevTools console commands added to the existing `window.__polar` namespace in `main.ts`:

```js
__polar.writeAlpha()          // alpha-slider ← flightState.alpha_deg
__polar.writeBeta()           // beta-slider  ← flightState.beta_deg
__polar.writeAirspeed()       // airspeed-slider ← flightState.airspeed
__polar.writeVelocityVector() // all three at once
__polar.wvv()                 // shorthand alias
```

### Implementation Details
- `_writeSlider(id, value)` — local helper defined just before the `__polar` object literal. Reads `el.min`/`el.max`, clamps the value, sets `el.value`, fires `new Event('input', { bubbles: true })` so `readState()` → `onChange()` picks it up immediately (labels update, charts refresh on next throttle tick).
- Logs the written value + a clamp note if the value exceeded the slider range (e.g. airspeed max = 80 m/s).
- `writeVelocityVector` / `wvv` call the individual methods via `window.__polar` to stay DRY.

### Why It's Safe
- **During sim**: `simStateToFlightState()` spreads `...base` then OVERRIDES `alpha_deg`, `beta_deg`, `airspeed` from the physics integrator. Slider writes have zero effect on physics.
- **After sim stops**: `readState()` drives again. Sliders now hold the last trim condition — static polar viewer shows aerodynamics at that trim.
- **No feedback loop**: the sim never writes alpha/beta/airspeed back to sliders. Flow is one-directional.

### Future Extension: "Lock In Trim"
The same `_writeSlider` pattern can write CONTROL INPUTS (left/right hand, weight shift, pitch/yaw/roll throttle). Those ARE read by the sim each frame via `getBaseState()`. Writing them would immediately shift the physics — which is the desired "lock in trim" behavior. No feedback loop risk because the sim doesn't write those fields back.

Suggested future commands:
```js
__polar.writeControls()   // write all sim-driving control inputs to their sliders
__polar.writeTrim()       // write velocity vector + controls (full trim snapshot)
```

Key slider IDs for controls: `left-hand-slider`, `right-hand-slider`, `weight-shift-slider`, `ws-pitch-slider`, `ws-yaw-slider`, `ws-roll-slider`, `ws-hip-camber-slider`, `ws-leg-bend-slider`.
